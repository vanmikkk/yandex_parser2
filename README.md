# Yandex Reviews Parser

SPA-приложение для авторизации пользователя, сохранения ссылки на
организацию в Яндекс Картах и фонового сбора отзывов с отображением
результатов с пагинацией.

## Стек

### Backend

-   PHP 8.5
-   Laravel 12
-   Laravel Sanctum
-   MySQL
-   Laravel Queue
-   Node.js
-   Puppeteer

### Frontend

-   Vue 3
-   Composition API
-   Vite

## Возможности

-   авторизация по логину и паролю;
-   один тестовый пользователь, регистрация отсутствует;
-   сохранение ссылки на организацию в Яндекс Картах;
-   серверная валидация URL;
-   получение информации об организации:
    -   название;
    -   средний рейтинг;
    -   количество оценок;
    -   количество отзывов;
-   получение всех доступных отзывов в пределах лимита Яндекса;
-   сбор до 600 последних опубликованных отзывов;
-   пагинация отзывов по 50 элементов без перезагрузки страницы;
-   отображение:
    -   автора;
    -   даты;
    -   текста;
    -   оценки;
-   запуск парсинга в фоне через Laravel Queue;
-   отображение прогресса парсинга;
-   повторный запуск парсинга;
-   обработка ошибок парсинга;
-   защита от параллельного повторного запуска одной организации.

Яндекс официально указывает, что в Картах и Личном кабинете Яндекс
Бизнеса доступны только последние 600 опубликованных отзывов. Поэтому
приложение ограничивает сохраняемый набор 600 отзывами.

# API

Все API-методы приложения находятся под `/api`.

Защищённые endpoints требуют аутентификации через Laravel Sanctum. Для
first-party SPA используется cookie-based session authentication с
CSRF-защитой.

## Authentication

### `POST /api/login`

Авторизация пользователя.

**Request:**

``` json
{
    "email": "test@example.com",
    "password": "password"
}
```

**Success: `204 No Content`**

После успешной авторизации Laravel создаёт сессию, которая используется
последующими запросами SPA.

### `POST /api/logout`

Завершает текущую пользовательскую сессию.

**Response: `204 No Content`**

### `GET /api/me`

Возвращает текущего авторизованного пользователя.

**Response:**

``` json
{
    "user": {
        "id": 1,
        "name": "Test User",
        "email": "test@example.com"
    }
}
```

Если пользователь не авторизован:

``` text
401 Unauthorized
```

# Organization API

## `GET /api/organization`

Возвращает сохранённую организацию и текущее состояние парсинга.

**Response:**

``` json
{
    "organization": {
        "id": 1,
        "yandex_url": "https://yandex.ru/maps/...",
        "yandex_id": null,
        "name": "Название организации",
        "rating": "4.80",
        "ratings_count": 1250,
        "reviews_count": 473,
        "last_parsed_at": "2026-09-16T10:30:00.000000Z",
        "parse_status": "completed",
        "parse_progress": 100,
        "parse_error": null
    }
}
```

Возможные значения `parse_status`:

``` text
idle
running
completed
failed
```

Frontend использует этот endpoint для отображения текущего состояния
фонового парсинга.

## `POST /api/organization`

Сохраняет URL организации и запускает парсинг.

**Request:**

``` json
{
    "yandex_url": "https://yandex.ru/maps/..."
}
```

Перед сохранением выполняется серверная валидация URL.

Проверяются:

-   корректность URL;
-   разрешённый домен Яндекс;
-   путь `/maps`;
-   наличие раздела «Отзывы» --- через `tab=reviews` либо URL-путь
    `/reviews/`.

**Success: `202 Accepted`**

``` json
{
    "message": "Organization saved. Parsing started.",
    "organization": {
        "id": 1,
        "yandex_url": "https://yandex.ru/maps/...",
        "parse_status": "running",
        "parse_progress": 0,
        "parse_error": null
    }
}
```

Сам парсинг внутри HTTP-запроса не выполняется. Endpoint только
сохраняет настройки и ставит `ParseOrganizationReviewsJob` в очередь.

Если парсинг уже выполняется:

``` text
409 Conflict
```

## `POST /api/organization/refresh`

Повторно запускает парсинг сохранённой организации.

**Request body:** отсутствует.

**Success: `202 Accepted`**

``` json
{
    "message": "Parsing started.",
    "organization": {
        "id": 1,
        "parse_status": "running",
        "parse_progress": 0,
        "parse_error": null
    }
}
```

Если предыдущий парсинг ещё выполняется:

``` text
409 Conflict
```

## `GET /api/organization/reviews?page=1`

Возвращает отзывы организации с серверной пагинацией.

Размер страницы:

``` text
50 reviews
```

Пример:

``` text
GET /api/organization/reviews?page=2
```

**Response:**

``` json
{
    "current_page": 2,
    "data": [
        {
            "id": 51,
            "organization_id": 1,
            "external_id": "review-id",
            "author": "Имя автора",
            "rating": 5,
            "text": "Текст отзыва",
            "published_at": "2026-09-10T12:00:00.000000Z"
        }
    ],
    "per_page": 50,
    "total": 473,
    "last_page": 10
}
```

Frontend использует `current_page`, `last_page` и `total` для построения
пагинации.

Во время выполнения Job frontend периодически запрашивает:

``` text
GET /api/organization
```

и получает актуальные `parse_status` и `parse_progress`.

После завершения парсинга frontend загружает отзывы через:

``` text
GET /api/organization/reviews?page=1
```

# HTTP-коды

      Код Значение
  ------- ---------------------------------------
    `200` Успешный GET-запрос
    `202` Парсинг поставлен в очередь
    `204` Успешный login/logout без тела ответа
    `401` Пользователь не авторизован
    `409` Парсинг уже выполняется
    `422` Ошибка валидации данных
    `404` Организация не найдена
    `500` Внутренняя ошибка сервера

Такое разделение позволяет frontend не зависеть от реализации парсера:
Vue работает только с API и состоянием организации, а работа с Яндекс
Картами остаётся на backend.

# Парсинг Яндекс Карт

## Почему не используется официальный API

Для задачи требуется получение отзывов организации.

Официального API Яндекс Карт для получения полного списка отзывов
организации в используемом сценарии нет, поэтому получение отзывов
выполняется через веб-интерфейс Яндекс Карт.

При исследовании страницы было обнаружено, что веб-приложение Яндекс
Карт само получает отзывы через внутренние HTTP-запросы. Однако прямое
воспроизведение таких запросов с backend оказалось нестабильным: запрос
зависит от браузерного контекста, сессии и параметров, сформированных
самим приложением.

Поэтому в качестве основного способа выбран браузерный парсинг.

## Выбранный подход: Puppeteer

Для загрузки страницы используется Puppeteer.

Puppeteer запускает Chrome/Chromium программно и позволяет работать с
DOM и сетевыми событиями страницы.

Текущий парсер:

1.  открывает переданный URL Яндекс Карт;
2.  ждёт появления блока отзывов и проверяет наличие контейнера отзывов;
3.  получает информацию об организации;
4.  перехватывает ответы внутренних запросов `fetchReviews`;
5.  собирает отзывы из ответов браузера;
6.  прокручивает контейнер отзывов, чтобы Яндекс подгружал следующие
    страницы;
7.  удаляет дубликаты по внешнему `reviewId`;
8.  использует DOM для первоначально отображённых отзывов, если сетевые
    ответы с отзывами ещё не были получены;
9.  останавливается после получения всех доступных отзывов либо после
    достижения лимита 600;
10. проверяет полноту результата;
11. сохраняет результат во временный JSON-файл;
12. Laravel сохраняет данные в MySQL.

Таким образом, JavaScript Яндекс Карт выполняется внутри браузера, а не
воспроизводится вручную на backend.

Парсер работает в headless-режиме. Для браузерной сессии задаётся
User-Agent и язык запросов, а между действиями используются паузы.

# Сравнение подходов

## 1. Прямой HTTP-запрос к внутреннему JSON

### Плюсы

-   высокая скорость;
-   небольшое потребление памяти;
-   не требуется запуск Chrome;
-   удобно масштабировать большое количество запросов.

### Минусы

-   внутренний endpoint не является публичным API;
-   формат запроса и ответа может измениться;
-   запросы могут зависеть от cookies, session ID, CSRF и других
    параметров браузерной сессии;
-   необходимо самостоятельно воспроизводить браузерный контекст;
-   изменение внутренних параметров может полностью сломать парсер.

Этот подход был исследован в процессе разработки, но для финального
варианта не выбран как основной.

## 2. Headless Browser / Puppeteer

### Плюсы

-   выполняется JavaScript страницы;
-   используется реальный DOM;
-   можно наблюдать сетевые запросы браузера;
-   не требуется вручную воспроизводить весь контекст внутренних
    HTTP-запросов;
-   подходит для динамически загружаемых отзывов;
-   удобнее диагностировать изменения страницы.

### Минусы

-   значительно большее потребление CPU/RAM;
-   запуск браузера занимает дополнительное время;
-   один процесс парсинга тяжелее обычного HTTP-запроса;
-   при большом количестве организаций необходимо ограничивать
    параллелизм браузеров.

Для данного тестового выбран Puppeteer как практически воспроизводимый
вариант для динамической страницы Яндекс Карт.

# Устойчивость к изменениям страницы

Парсер не должен молча сохранять пустой или неполный результат, если
Яндекс изменил структуру страницы или механизм загрузки отзывов.

Перед сбором проверяется:

-   наличие заголовка блока отзывов;
-   наличие контейнера отзывов.

Во время работы дополнительно контролируется:

-   наличие корректных JSON-ответов внутренних запросов;
-   количество полученных отзывов;
-   количество новых отзывов;
-   количество дубликатов;
-   количество оставшихся отзывов;
-   последняя обработанная страница;
-   достижение ожидаемого количества отзывов.

Если структура страницы изменилась, страница недоступна, браузер получил
ограниченную страницу или отзывы перестали загружаться, парсер не должен
считать такой результат успешным. При отсутствии прогресса после
нескольких попыток прокрутки задача завершается ошибкой. Laravel
переводит Job в состояние `failed` и сохраняет текст ошибки.

Отдельно проверяется полнота итогового результата: если Яндекс сообщил
доступное количество отзывов, а парсер собрал меньше и не достиг
последней доступной страницы, результат считается неполным и не
сохраняется в базу.

Это позволяет отличить корректный результат с меньшим количеством
отзывов от ситуации, когда механизм сбора перестал работать.

В процессе работы логируются:

-   номер страницы;
-   количество полученных отзывов;
-   количество новых отзывов;
-   количество дубликатов;
-   текущее количество собранных отзывов;
-   общее количество отзывов;
-   количество оставшихся отзывов;
-   последняя обработанная страница.

# Ограничение в 600 отзывов

Яндекс указывает, что пользователю доступны последние 600 опубликованных
отзывов.

Поэтому в парсере используется:

``` js
const MAX_AVAILABLE_REVIEWS = 600;
```

Если у организации:

-   473 отзыва → собираются все 473;
-   600 отзывов → собираются все 600;
-   1822 отзыва → сохраняются 600 доступных для пользовательского
    сценария отзывов.

# Очередь и фоновые задачи

Парсинг не выполняется непосредственно внутри HTTP-запроса.

Это необходимо, поскольку запуск браузера и загрузка сотен отзывов может
занимать десятки секунд или больше.

`ParseOrganizationReviewsJob` имеет:

-   до 3 попыток выполнения;
-   timeout 900 секунд;
-   состояния `running`, `completed`, `failed`;
-   прогресс от 0 до 100%;
-   сохранение текста последней ошибки.

Во время работы Node.js отправляет прогресс через stderr:

``` text
PROGRESS: 150/600
PROGRESS: 300/600
PROGRESS: 450/600
PROGRESS: 600/600
```

Laravel читает эти сообщения и обновляет `parse_progress`.

Frontend периодически получает актуальное состояние организации через
API и показывает прогресс пользователю.

Для масштаба около 50 организаций задачи должны выполняться через
очередь с ограниченным количеством одновременно работающих browser
workers, а не параллельно внутри одного HTTP-запроса.

# Защита от повторного запуска

Если парсинг уже выполняется, повторный запуск не создаёт вторую
параллельную задачу.

API возвращает HTTP `409`.

Это предотвращает ситуацию, когда несколько запросов одновременно
запускают браузер для одной и той же организации.

# Дубликаты и повторный парсинг

Каждый отзыв сохраняется с внешним идентификатором:

``` text
organization_id + external_id
```

В базе используется уникальное ограничение:

``` text
unique(organization_id, external_id)
```

При новом успешном парсинге текущий набор отзывов организации
синхронизируется заново: старые сохранённые отзывы удаляются и
заменяются актуальным успешно собранным набором.

Это позволяет повторно запускать парсер без накопления дублей.

Если парсинг завершился ошибкой или вернул неполный результат,
сохранение нового набора отзывов не выполняется.

# Обработка ошибок

Ошибки обрабатываются на нескольких уровнях.

## URL

Некорректная ссылка не проходит Laravel validation.

Проверяется:

-   корректность URL;
-   разрешённый домен Яндекс;
-   путь `/maps`;
-   наличие раздела «Отзывы».

## Парсер

Ошибки Puppeteer и Node.js передаются обратно в Laravel.

В частности, если вместо ожидаемой страницы Яндекс возвращает
ограниченную страницу или изменяется структура отзывов, парсер завершает
работу с ошибкой, а не сохраняет пустой результат как успешный.

## Queue Job

При ошибке:

``` text
parse_status = failed
```

и сохраняется:

``` text
parse_error
```

После исчерпания попыток Laravel Queue вызывает `failed()` Job.

## Frontend

Vue отображает пользователю:

-   состояние загрузки;
-   прогресс;
-   сообщение об ошибке;
-   состояние успешно завершённого парсинга.

# Anti-ban / нагрузка

Парсер не пытается отправлять большое количество параллельных
HTTP-запросов к Яндексу.

В рамках одной задачи используется один экземпляр браузера и
последовательная загрузка страниц через штатный механизм страницы. Между
действиями присутствуют паузы, а отзывы загружаются через обычную
прокрутку контейнера.

В текущем тестовом проекте также задаётся User-Agent браузера и язык
запросов. Ротация User-Agent и proxy не реализована.

Для production-версии при масштабировании на десятки организаций
дополнительно предусмотрел бы:

-   ограничение количества одновременно работающих браузеров;
-   ограничение concurrency очереди;
-   exponential backoff для повторных попыток;
-   отдельные статусы `blocked`, `retrying`, `timeout`;
-   обработку HTTP 403/429 и других признаков блокировки;
-   управляемую ротацию proxy при наличии такой инфраструктуры;
-   мониторинг длительности и частоты ошибок парсинга.

Для тестового проекта эти механизмы не усложнялись искусственно:
реализованы очередь, повторные попытки, последовательная браузерная
загрузка и паузы.

# Idempotency и история

Повторный запуск парсинга не должен создавать дубликаты.

Для этого отзыв идентифицируется внешним `reviewId`, а в базе существует
уникальная комбинация:

``` text
organization_id + external_id
```

В текущей версии база хранит актуальное состояние отзывов организации.

История изменений в тестовом проекте не реализована полностью, но для
production-версии её можно добавить через снимки парсинга:

``` text
parse_snapshots
    id
    organization_id
    parsed_at
    rating
    ratings_count
    reviews_count
```

и связанные записи:

``` text
snapshot_reviews
    snapshot_id
    external_id
    author
    rating
    text
    published_at
```

Тогда каждый успешный запуск создавал бы новый снимок, а два снимка
можно было бы сравнить и определить:

-   новые отзывы;
-   изменённые отзывы;
-   исчезнувшие отзывы;
-   изменение рейтинга;
-   изменение количества оценок;
-   изменение общего количества отзывов.

# Структура проекта

Основная логика браузерного парсинга:

``` text
backend/scripts/yandex-reviews.cjs
```

Laravel-интеграция с Node.js:

``` text
backend/app/Services/YandexParserService.php
```

Фоновая задача:

``` text
backend/app/Jobs/ParseOrganizationReviewsJob.php
```

Контроллеры отвечают только за HTTP/API-уровень: валидацию, сохранение
настроек, постановку Job в очередь и выдачу данных frontend.

# Локальный запуск

## Требования

-   PHP 8.5+
-   Composer
-   Node.js
-   MySQL
-   Chrome/Chromium, устанавливаемый/используемый Puppeteer
-   Laravel Queue worker

## Backend

Перейти в каталог:

``` bash
cd backend
```

Установить PHP-зависимости:

``` bash
composer install
```

Установить Node-зависимости:

``` bash
npm install
```

Создать `.env` на основе `.env.example`.

Для Linux/macOS:

``` bash
cp .env.example .env
```

Для Windows можно скопировать `.env.example` вручную и назвать файл
`.env`.

Сгенерировать ключ:

``` bash
php artisan key:generate
```

Настроить подключение к MySQL в `.env`.

Выполнить миграции и seed:

``` bash

```

Запустить Laravel:

``` bash
php artisan serve
```

В отдельном терминале запустить Queue Worker:


# Переменные окружения

Основные настройки Laravel находятся в `.env`.

Пример:

``` env
APP_URL=http://127.0.0.1:8000

DB_CONNECTION=mysql
DB_HOST=127.0.0.1
DB_PORT=3306
DB_DATABASE=...
DB_USERNAME=...
DB_PASSWORD=...

QUEUE_CONNECTION=database
```

Реальные credentials, cookies, токены и другие секретные значения в
репозиторий не добавляются.

# Production / hosting

Для запуска на хостинге помимо PHP и MySQL необходимы:

-   Node.js;
-   Chromium/Chrome и системные зависимости для него;
-   Laravel Queue Worker;
-   настроенное файловое хранилище для временного JSON результата;
-   корректно настроенные `.env` и database/queue connection.

Queue Worker должен работать постоянно, иначе поставленные задачи
парсинга не будут выполняться.

Для Linux production-среды Queue Worker и Node.js процессы следует
запускать через process manager, например Supervisor или systemd.

Headless-режим выбран специально, чтобы браузер мог работать на сервере
без графического интерфейса.

# Что можно улучшить при наличии дополнительного времени

1.  Добавить полноценную историю изменений отзывов.
2.  Разделить парсинг и сохранение результатов через staging-таблицу.
3.  Добавить отдельные статусы `blocked`, `retrying`, `timeout`.
4.  Реализовать ограничение concurrency для browser workers.
5.  Добавить автоматические тесты парсера на сохранённых HTML/JSON
    fixtures.
6.  Добавить мониторинг Queue и длительности парсинга.
7.  Добавить Docker Compose для запуска Laravel, MySQL, Node.js и Queue
    Worker одной командой.
8.  Добавить больше независимых от CSS-селекторов способов обнаружения
    элементов страницы.
9.  При масштабировании рассмотреть пул браузеров вместо запуска
    отдельного браузера для каждой задачи.
10. Добавить полноценную стратегию proxy/User-Agent rotation и backoff
    для production-нагрузки.

# Примечание

Проект предназначен для демонстрации архитектуры и подхода к сбору
данных из динамического веб-приложения.

Парсер использует публично доступную веб-страницу Яндекс Карт и
браузерный сценарий работы с ней. Формат внутренних запросов и структура
страницы не являются стабильным публичным API, поэтому в production
необходимо предусмотреть регулярную проверку и адаптацию парсера при
изменениях Яндекс Карт.
